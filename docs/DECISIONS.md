## 2026-07-20 — Five-layer pipeline, each behind a Protocol + registry-factory seam

**Decision:** Materials, DFT, transport, thermal, and manufacturability layers each expose a `Protocol` (e.g. `DFTBackend`) plus a `get_backend(name, **params)` factory. `orchestration/pipeline.py` never imports a concrete backend class — only the factory. Every `Result` dataclass carries a shared `ProvenanceInfo` (backend name, `is_stub` flag, tool version, run id, git commit).
**Why:** The build-order decision is "broad-but-shallow across all layers first, then deepen into one fully validated device" — that only works cleanly if swapping a stub backend for a real solver (Quantum ESPRESSO, DEVSIM, Kwant, FEniCSx, Elmer) is a one-line config change, not a codebase-wide ripple. The `is_stub` provenance flag also directly enforces this repo's core rule: never present a generated number as if a real solver produced it.
**Trade-off accepted:** Some upfront interface design before any real solver is actually wired — real solvers may need fields not yet modeled (e.g. DEVSIM doping profiles). Mitigated with an `extra: dict[str, Any]` escape hatch on every Result type; expect a documented revision once real backends land, not a silent one.
**How it's going:** Scaffolded same session. Materials layer (M1) and validation layer (M2) built with real logic; DFT/transport/thermal/manufacturability stub+real seam (M3) not yet started.

## 2026-07-20 — Lightweight CI despite no CI in the closest sibling repo

**Decision:** Add GitHub Actions CI (`pip install -e ".[dev]"`, no conda) running only tests that need zero heavy binaries (schema, stub backends, %-error computation, report generation, orchestration wiring with stubs, `.bats` scripts). Tests needing a real heavy solver are marked `requires_real_solver` and excluded (`pytest -m "not requires_real_solver"`).
**Why:** A simulator whose whole claim is honest, checkable accuracy needs a green, reproducible test signal on every change. Full DFT/NEGF/FEA runs are too heavy for CI compute, so CI scope is deliberately narrower than the full test suite.
**Trade-off accepted:** CI doesn't cover the heavy-solver paths at all — those stay locally-verified only. Worth revisiting whether the lightweight real DEVSIM/Kwant toy-model tests (both pip-installable, fast) can run in CI too once M3 lands.

## 2026-07-20 — `MaterialRecord.lattice_constant_angstrom` made optional; monoclinic oxides use `extra`

**Decision:** `lattice_constant_angstrom` and `band_gap_eV` on `MaterialRecord` are now `float | None` instead of required. Added an `extra: dict[str, Any]` escape hatch to `MaterialRecord`, matching the pattern already used on every `Result` dataclass. Monoclinic bulk oxides (HfO2, ZrO2 — the gate dielectrics) store their real a/b/c/β lattice parameters in `extra["lattice_parameters"]` instead of forcing them into the single-scalar field.
**Why:** Discovered while seeding real HfO2/ZrO2 data from Materials Project (mp-352, mp-2858) — the original schema assumed a single scalar lattice constant (a=b), which only holds for the hexagonal 2D materials (TMDs) this project centers on. Monoclinic P2₁/c oxides have independent lattice parameters that don't reduce to one number. This is exactly the kind of interface-churn risk already flagged in `docs/ROADMAP.md`'s "Known interface risk" note — logging it here instead of silently reshaping the field.
**Trade-off accepted:** `lattice_constant_angstrom` being optional means downstream code (once transport/thermal backends exist) must handle `None` explicitly rather than assuming every material has a scalar lattice constant.
**How it's going:** Fixed same session, before any real backend depends on the field.

## 2026-07-21 — Materials scale-up via direct dataset download, not search-engine lookup; real avg_elec_mass bug fixed

**Decision:** Scaled the materials database (graphene, hBN, black phosphorus added real; WS2's standing all-null gap resolved with real data; MoTe2/WTe2 confirmed genuinely absent, not just unfound) by downloading the actual JARVIS-DFT `dft_2d` dataset directly (the exact figshare URL used by jarvis-tools' own source code, confirmed by reading that source on GitHub rather than guessing a file ID) and parsing it by hand, instead of relying on web-search indexing of individual NIST pages (which had failed to surface WS2's real entry in an earlier session). While doing this, found and fixed a real bug in `materials/sources/jarvis_dft.py`: `FIELD_MAP` mapped `effective_mass_electron/hole` to the dataset's flat `avg_elec_mass`/`avg_hole_mass` fields, but those are an *average across x, y, z tensor components* — for a layered 2D material the out-of-plane (z) component is enormous and dominates the average, making it physically the wrong quantity for a channel-transport effective mass. The correct in-plane value lives in `effective_masses_300K.n[0]`/`.p[0]`, confirmed by cross-checking against MoS2's already-seeded value (0.51 m0, matching the HTML-page-fetched value from the 2026-07-20 session exactly).
**Why:** This bug had never actually run against real data before (the module was written but never executed against the live dataset) — the seed data for MoS2/WSe2/HfO2/ZrO2 was correct because it came from direct HTML-page fetches, not this code path. Running the code path for real materials for the first time this session is exactly what surfaced the latent bug — a concrete instance of "never run against real data" risk materializing, caught before it silently corrupted new seed data.
**Trade-off accepted:** Black phosphorus's genuine lattice/effective-mass anisotropy (a≠b, armchair≠zigzag effective mass) doesn't fit `jarvis_dft.py`'s flat `FIELD_MAP` extraction logic — hand-seeded instead of auto-fetched, with `JVASP_IDS` deliberately not including it, flagged as a fold-in-later item once the module supports the `extra` escape hatches. Graphene's `effective_masses_300K` is `"na"` in the source data (no parabolic mass for a Dirac cone) — a genuine physical/schema mismatch, not a citation gap, tracked via a new `extra["band_structure_type"] = "gapless"` field.
**How it's going:** Done same session. 10 materials now seeded: MoS2, WSe2, HfO2, ZrO2, hBN, WS2 real and citation-complete; graphene real but deliberately gapless (`extra["band_structure_type"]`); black phosphorus real but deliberately anisotropic (`extra["lattice_parameters"]`/`extra["effective_mass_tensor"]`); MoTe2/WTe2 honest null placeholders (confirmed absent from the dataset, not just unfound). 84 tests passing, including new tests covering the gapless/anisotropic/resolved-WS2 cases.

## 2026-07-21 — Real Kwant backend verified working; DEVSIM blocked on sandbox BLAS; both real bugs found and fixed by actually running against installed packages

**Decision:** Attempted real installs of DEVSIM and Kwant in this session's sandbox (a `uv`-managed venv, no conda available, no root). Kwant is now genuinely working end-to-end (`transport/kwant_backend.py`, verified against real installed kwant 1.5.0). DEVSIM's Python package installs cleanly but cannot be verified in this specific sandbox (see next entry).
**Why / what was found:**
- Kwant's published PyPI sdist ships a pre-generated Cython C file incompatible with NumPy 2.x's C API (`PyArray_Descr` has no member `subarray`) — required a from-source rebuild (`python setup.py build_ext --cython`) plus installing `sympy` and `tinyarray` as real runtime deps (neither was in the original dependency notes — both confirmed necessary by actually running the code, not guessed).
- Running the real package against my original `kwant_backend.py` immediately surfaced a real API bug: `syst[template.shape(shape, start)] = onsite` is not a real kwant 1.5 API (`Builder` has no `.shape` attribute) — the real API is `syst.fill(template, shape_fn, start)`, with symbolic Hamiltonian parameters (V, hbar, m_e) passed via `kwant.smatrix(..., params=dict(...))`, not overridden per-site. Fixed by reading kwant's own bundled tutorial docs (`doc/source/tutorial/discretize.rst`) rather than guessing further.
- A second real bug: the original default lattice spacing (`channel_length_nm/200`) combined with a full-width (100nm) device produced a ~200,000-site lattice, which made `kwant.smatrix()` hang indefinitely against kwant's SciPy dense fallback solver (no MUMPS available). Fixed with a real, measured site-count cap (`_MAX_TRACTABLE_SITES`) that raises a clear `LatticeTooLargeError` instead of hanging silently.
- After both fixes, a real toy-geometry run (10nm x 5nm channel) completed in ~8 seconds and produced a physically sensible I-V curve (current monotonically non-decreasing with Vgs, as expected for a barrier-lowering gate model).
**Trade-off accepted:** The default CLI geometry (100nm channel width) now correctly refuses to run with kwant rather than hanging — real device-scale Kwant runs need either a narrower toy width or explicit `lattice_spacing_nm` tuning; this is a genuine Phase-1 scope limit (documented, not silently papered over), not a bug.
**How it's going:** `transport/kwant_backend.py` genuinely verified working 2026-07-21. `tests/e2e/test_real_pipeline.py` covers both the real run and the lattice-size guard.

## 2026-07-21 — DEVSIM blocked on missing BLAS/LAPACK in this sandbox (environment limitation, not a DEVSIM defect)

**Decision:** DEVSIM's `_setup_drift_diffusion()` stays `NotImplementedError` (as originally planned) — but additionally, DEVSIM cannot even be *imported* in this session's sandbox, for a reason unrelated to that unimplemented function.
**Why:** DEVSIM's compiled extension `dlopen`s `libopenblas.so`/`liblapack.so`/`libblas.so` at import time, expecting standard (unmangled) BLAS/LAPACK symbol names. This sandbox has no system package manager access (no root, `apt-get` fails with permission denied even with sandbox escalation attempted) and no conda/mamba installed. The only BLAS present is bundled inside numpy/scipy wheels with renamed symbols (e.g. `scipy_dgemm_` not `dgemm_`), specifically to avoid exactly this kind of collision — DEVSIM's loader correctly rejects them as "MISSING SYMBOLS." This is a real, verified environment gap, not a guess: multiple concrete approaches were tried (pointing `DEVSIM_MATH_LIBS` at scipy's bundled library; searching for a standalone-symbol-name BLAS wheel on PyPI) and all failed for this specific reason.
**Trade-off accepted:** DEVSIM's import-level failure is now an explicit, tested, documented sandbox limitation (`tests/e2e/test_real_pipeline.py::test_devsim_import_fails_in_this_sandbox_missing_blas`) rather than silently skipped. `environment.yml`'s conda-based approach should not hit this — conda's own numpy/scipy normally pull in a correctly-named OpenBLAS as a transitive dependency — but this was **not possible to verify end-to-end in this session** (no conda available here). Flagged as a real open item for the self-hosted runner, not assumed fixed.
**How it's going:** Documented and tested as a known sandbox limitation. Re-verify on the actual self-hosted runner once `scripts/setup_env.sh` has run there.

## 2026-07-21 — Real HotSpot .flp/.lcf file formats were wrong; fixed by building and running the actual binary against its own bundled examples

**Decision:** Cloned and built the real HotSpot binary (`git clone` + `make`, succeeded cleanly with no missing dependencies) and rewrote `thermal/hotspot_backend.py` against the *verified* real file formats, found by reading HotSpot's own bundled example files (`examples/example4/`, a real 3D-IC multi-layer case) rather than continuing to guess.
**Why / what was found:**
- The `.flp` (floorplan) column order is `<Unit> <Width> <Height> <X> <Y>` (all meters) — the original code had it as `<Unit> <X> <Y> <Width> <Height>`, silently wrong until checked against a real example file.
- The `.lcf` (layer config) format is a **7-line block per layer** (layer number; lateral heat flow Y/N; power dissipation Y/N; specific heat capacity in J/(m³·K); resistivity in (m·K)/W — the reciprocal of thermal conductivity, not thermal conductivity itself; thickness in meters; floorplan filename), blank-line separated — not one tab-separated line per layer as originally written.
- The real command line needs `-detailed_3D on` (for per-layer heterogeneous floorplans) and **both** `-grid_steady_file` and `-steady_file` together, neither of which the original sketch had fully right.
- HotSpot's grid model requires `-grid_rows`/`-grid_cols` to be powers of two — the shipped `template.config`'s default of 39 is rejected outright with a clear error. Not documented anywhere obvious; found by running the real binary and reading its error message.
- `materials/schema.py`'s `MaterialRecord` has no volumetric specific-heat-capacity field at all — a real, previously-unnoticed schema gap. `hotspot_backend.py` uses an explicitly-flagged generic default (matching HotSpot's own example value for silicon) rather than pretending it's material-specific.
- `scripts/setup_env.sh` never actually vendored `hotspot.config` (HotSpot ships `template.config`, a different filename) — a real gap that was flagged as a known risk when the script was first written, now fixed by copying it during setup.
- A minimal real 2-layer steady-state run (10µm-scale toy device) completed successfully and produced physically sensible output (powered channel layer hotter than the unpowered adjacent layer, both hotter than heatsink-adjacent nodes).
**Trade-off accepted:** Verifying the full Python-wrapped pipeline (not just the standalone binary CLI) end-to-end at realistic device scale (100nm-wide channel, 64×64 grid) took real wall-clock time in this session's sandbox — separately, this session also discovered and killed a runaway leftover process from an earlier (pre-fix) Kwant test that had been silently consuming ~14 CPU cores for 40+ minutes in the background, which was the actual cause of several apparent "hangs" misattributed to HotSpot itself before the real cause was found. A genuine lesson: verify system load (`uptime`, `ps aux`) before concluding a real-solver integration is broken, in a shared sandbox.
**How it's going — RESOLVED same session.** File formats verified correct via a real successful manual run at 10µm scale. The realistic-scale (100nm) performance issue was root-caused, not just described: bisected device size against a fixed 16×16 grid (1µm still too slow; 100µm fast) to find the real boundary, rather than guessing at config parameters again (a first naive attempt to shrink `s_sink`/`s_spreader` had made things worse, not better). The actual cause: HotSpot's grid model is designed for chip-level floorplans (many functional blocks across a realistically-sized die), not a bare nm-scale device treated as if it were the entire chip — an architectural mismatch, not a tunable numerical parameter. Fixed with `_pad_to_die_footprint()`: the real device becomes one named, powered block inside a synthetic 100µm×100µm die footprint, with the remaining area filled by two unpowered "fill" blocks of the same layer material (a corner+two-strip tiling, verified gap-free and overlap-free). This is physically motivated, not just a numerical trick — a real transistor is never thermally isolated in a cm-scale package; it always sits within a realistically-sized surrounding die. Hit one more real, fast-failing requirement along the way (found via HotSpot's own clear error messages, not guessed): only layers marked power-dissipating in the `.lcf` contribute *any* units to the `.ptrace` header at all — non-powered layers' units (and, by extension, a powered layer's own unpowered fill blocks) must either be entirely absent (non-powered layers) or explicitly zero (fill blocks within a powered layer), confirmed against HotSpot's own bundled 3D-IC example's real `.ptrace` file. **Verified end-to-end at the CLI's actual default device scale** (100nm × 20nm), ~58s, with physically sensible output (45.15°C, consistent with a tiny device's heat spreading efficiently into a much larger synthetic die). `extra["synthetic_die_padding_applied"]` flags every result where this applies, so it's never silently mistaken for the device's real footprint. Directly corroborates `docs/M5_PLAN.md`'s independent recommendation (written before this fix) to treat scale mismatch as a real, structural modeling concern, not an edge case.

## 2026-07-21 — M6 heterostructure search: no a priori n/p role assignment; carrier_type added to transport stub first

**Decision:** Before building `orchestration/heterostructure.py`, added a `carrier_type` param (`"electron"` default | `"hole"`) to `transport/stub.py`, selecting `effective_mass_electron` vs `effective_mass_hole`. The search itself (`heterostructure.py`) runs every candidate channel material (a curated list of 7 real 2D materials from the materials-scale-up table, excluding HfO2/ZrO2 gate dielectrics) in **both** roles rather than assuming which materials are "n-type" or "p-type" ahead of time.
**Why:** Every transport calculation previously implicitly modeled an nFET regardless of which carrier actually dominates — meaningless for a genuine n/p-asymmetry search, since the whole point is comparing n-role vs p-role performance per material. Assuming the literature's MoS2-n/WSe2-WS2-p framing as ground truth (rather than testing it) would have made the "search" a foregone conclusion instead of a real one; running every candidate in both roles lets the actual computed numbers confirm or contradict that framing, and would surface a genuinely ambipolar candidate if one existed in the real data.
**Trade-off accepted / real finding:** Checked real data completeness against `dft/stub.py`'s required-fields gate — **only MoS2 and WS2 can run through the pipeline at all today**; WSe2 (the leading literature p-type candidate) is missing both effective masses, and the other 4 candidates are missing multiple fields. Ran the real numbers for MoS2/WS2 in both roles through the stub transport model and found that Ion and power (hence junction temp) move together in this simple long-channel model — a higher-mobility candidate always has both higher Ion (good) and higher Tj (bad). Neither material dominates the other in either role with today's stub model/data, so both Pareto fronts genuinely contain 2 members and `recommended_{n,p}_material_id` is correctly `None` — built to reflect this honestly (no forced single winner) rather than break the tie arbitrarily.
Separately, running the full pipeline for this search surfaced that `thermal/stub.py`'s lumped-RC model produces physically absurd absolute Tj values (hundreds of thousands of °C) at this device's nm-scale area against a bulk substrate thickness — the same scale-mismatch class already found and fixed for the real HotSpot backend via `_pad_to_die_footprint()`, but the stub never got an equivalent fix. `max_junction_temp_C` is kept as a search objective (still a real, ordinal/relative signal between candidates) but flagged explicitly as not physically meaningful in absolute terms, both in the CLI output and the module docstring — logged as an open `docs/ROADMAP.md` item rather than fixed here (out of this milestone's scope).
**How it's going:** `orchestration/heterostructure.py` + `qf heterostructure-search` CLI command built and verified 2026-07-21, 5 new tests passing (including "never silently drops an incomplete-data candidate"). Reused `pareto.py`'s `pareto_front()` unmodified, per its original design intent from the M3a plan; `sweep.py` wasn't applicable (it varies one param on one fixed material, not `material_id` itself). Biggest real blocker to a genuinely useful MoS2(n)/WSe2(p) pairing recommendation going forward: sourcing WSe2's missing effective mass data (new, higher-priority `docs/ROADMAP.md` item).

## 2026-08-04 — Physics-fidelity audit

Independent audit of device-physics modeling fidelity (provenance flags, boundary-condition/assumption documentation, unit consistency, stub-honesty) against real semiconductor-modeling conventions (BSIM-class boundary-condition documentation practice, IEEE/JEDEC device-characterization norms). Existing tests didn't catch this because `RunConfig`'s defaults are all-stub (`orchestration/config.py`), so the one existing real-run test (`test_export_chiplet_collateral_real_run_produces_real_verilog_a`) never exercised the mixed-provenance case. **Real bug found and fixed — `transport/kwant_backend.py:227` and `transport/stub.py`, `power_density_W_per_um2` divided by channel width twice instead of once by width and once by length.** Both backends compute `ion_uA_per_um` as current normalized by channel *width* (`I_total/W`, the standard on-current reporting convention), then had to normalize by device *area* (`W×L`) to get a power *density*. `power_density_W_per_um2 = ion*1e-6*vds / w_um` in both files re-divides by width a second time instead of dividing by length — dimensionally, `W` cancels out of the correct formula entirely (`P/(W·L) = (ion·W·V)/(W·L) = ion·V/L`), so the old formula computed `P/(W·W)` instead of `P/(W·L)`. Every downstream consumer (`thermal/stub.py:60`, `thermal/hotspot_backend.py:184,344,430`) recovers total device power by multiplying this field by the *real* `W×L` footprint area — so the bug silently mis-scaled total power (and therefore every downstream `max_junction_temp_C`, including real HotSpot runs) by a factor of `L/W` whenever `L ≠ W`. For this project's own repeatedly-used 20nm×100nm CLI-default geometry, `L/W = 0.2` — a 5x underestimate of real device power feeding the thermal solver. This is the same class of bug as the `mobility_degradation.py` scattering-coefficient unit mismatch found 2026-07-31 (dimensional mismatch that went uncaught because nothing checked the derivation against the formula's own units) — confirms that bug class wasn't fully swept last time. Fixed both backends to divide by `l_um` instead; added a pure-Python regression test in `tests/transport/test_stub.py` (`test_power_density_depends_on_length_not_width`, verifies both width-invariance and the exact expected formula) and a `requires_real_solver`-gated assertion in `tests/e2e/test_real_pipeline.py::test_kwant_backend_real_run` (can't run in this sandbox — no kwant installed — but will run on the self-hosted runner / real-solvers CI job). No test previously asserted a specific `power_density_W_per_um2` value, so nothing broke; full non-real-solver suite (188 tests) still green, `ruff`/`mypy` clean on every touched file (pre-existing lint findings in `chiplet_export.py`/`kwant_backend.py` confirmed present on `main` before this session's changes too, not introduced by them).

**Real finding, documented not fixed — `transport/kwant_backend.py`'s `dibl_mV_V` is not a measurement of real drain-induced barrier lowering.** Verified directly from the code (not a judgment call): `_make_potential(band_gap_eV, vgs, geometry)` takes only `band_gap_eV` and `vgs` — `V_ds` never enters the Hamiltonian/potential landscape passed to `kwant.smatrix()`. `_run_sweep(vds_low)` and `_run_sweep(vds_high)` therefore compute *identical* `transmission(V_gs)` curves; the only difference is the post-hoc linear `transmission * G0 * vds_value` scaling (Landauer's I=GV). Since `extract_vth_constant_current` finds `V_gs` at a fixed *absolute* current threshold, and the high-`V_ds` curve is the low-`V_ds` curve uniformly scaled up, the crossing point necessarily shifts to a lower `V_gs` at higher `V_ds` — producing a nonzero, correctly-*signed* `dibl_mV_V` (rough hand-derivation puts it in the 50-150 mV/V range for this project's default toy sweep, a plausible-looking real-DIBL magnitude) purely as an artifact of the extraction method, with zero real self-consistent electrostatics (drain-side band bending) modeled anywhere. This is exactly the kind of thing that could pass a casual read as real physics because the sign and rough magnitude look right. Not currently consumed anywhere downstream (`grep` confirms `dibl_mV_V`/`dibl_mV_per_V` appear only in `kwant_backend.py`, `extraction.py`, and `results.py` — not in the Pareto/heterostructure search or validation report), so no reported number is affected today, but the field is prominently returned on every real Kwant `TransportResult` and this session's earlier reading of `docs/DECISIONS.md`'s 2026-07-22 entry ("DIBL... wired into kwant_backend.py's new two-V_ds sweep") could easily be taken as "DIBL is now real" by a future reader. Documented in place (extended comment above the V_th/DIBL block, plus a new `extra["dibl_caveat"]` flag on every `TransportResult` this backend produces, matching the existing `contact_model`/`gate_type_physics_modeled` honesty-flag pattern) rather than fixed, because a real fix — giving the NEGF Hamiltonian actual `V_ds`-dependent electrostatics (e.g. a self-consistent Poisson-NEGF loop, or at minimum a linear potential ramp across the channel scaled by `V_ds`) — is real physics-modeling work requiring a scoping call on how much rigor is worth building now, not something to guess at inside an audit pass. **Open item for a domain expert:** decide whether `dibl_mV_V` should be (a) left as an honestly-flagged illustrative field until real `V_ds` electrostatics are built, or (b) removed/hidden until then so it can't be mistaken for validated output.

**No provenance-flag or unit bugs found elsewhere.** Grepped every `Result`/dataclass construction across `dft/`, `transport/`, `thermal/`, `manufacturability/` (11 construction sites total) — every one passes a non-optional `ProvenanceInfo` with `is_stub` set correctly for its backend kind (stub backends `True`, real backends — Kwant, HotSpot incl. `run_stacked()`, Poisson/Murphy/negative-binomial, Monte Carlo — `False`). **Decision:** Release the project publicly under Apache-2.0, with contributions accepted under a DCO sign-off (no CLA). Drive gmsh as a subprocess via a generated `.geo` script instead of `import gmsh`. Make the self-hosted `real-solvers` CI job `workflow_dispatch`-only.
**Why:** Apache-2.0 carries an explicit patent grant (relevant for semiconductor tooling) and matches DEVSIM's own license. A DCO is the lightest mechanism that still records contributors' right to submit. gmsh is GPL-2.0-or-later; every other GPL tool in the stack (Elmer, Quantum ESPRESSO, Wannier90) already sits behind a process or container boundary, and gmsh was the one exception imported in-process. The `.geo` language covers every operation the old code used (OCC boxes, `BooleanFragments`, bounding-box entity selection, named physical groups), so behaviour is unchanged; the four real mesh tests pass against the new path. On a public repo the old `pull_request` trigger would have let a fork PR run arbitrary code on the self-hosted machine — the `github.repository ==` guard does not stop that, because a fork PR's workflow runs in the base repository's context.
**Trade-off accepted:** Real-solver CI no longer runs automatically on each PR; a maintainer triggers it. Mesh generation now needs the `gmsh` executable (shipped by the same headless pip package) rather than the Python module.
**Found while doing this (not fixed, tracked in `docs/ROADMAP.md`):** the mesh's `adiabatic_boundary` group includes the internal SiO2/Si interface face at z = 0 — the old in-process code did the same. Harmless for FEniCSx exterior-facet measures, wrong for an Elmer boundary condition; fix before M5's Elmer backend consumes it.
